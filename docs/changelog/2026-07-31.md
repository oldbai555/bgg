**踩过的坑 —— 绝对不要再犯**：

> - **现象**：`ssh-copy-id -i id_ed25519_bgg_deploy.pub ubuntu@bgg-dev` 报 `All keys were skipped because they already exist`，但 `authorized_keys` 里只有个人密钥一行；用 `-i deploy_key` 测试 SSH 却能登录。**根因**：本机 `~/.ssh/config` 里 `bgg-dev` 配置了 `IdentityFile ~/.ssh/id_ed25519`，OpenSSH 在 deploy 公钥未真正写入服务器时仍会 fallback 到个人密钥成功登录，造成「deploy 密钥已生效」的假象；`ssh-copy-id` 的「已存在」检测也可能因同样原因误判。**正确做法**：写入公钥时用 `ssh-copy-id -f` 强制追加；验证时必须加 `-o IdentitiesOnly=yes -i ~/.ssh/id_ed25519_bgg_deploy`，确认输出 `deploy-only-ok`；再用 `ssh bgg-dev 'wc -l ~/.ssh/authorized_keys'` 确认变为 2 行。
> - **现象**：GitHub Actions 里不能写 `Host bgg-dev` 这种 SSH config 别名。**根因**：Runner 没有用户本地的 `~/.ssh/config`。**正确做法**：`DEPLOY_SSH_HOST` Secret 填服务器公网 IP 或可解析域名，不能填本地别名。
> - **现象**：飞书通知 / 自动部署只在 merge 到 `main` 后触发，开 PR 阶段不会跑。**根因**：`build-images`/`deploy-dev`/`notify-feishu` 均限定 `github.ref == refs/heads/main`。**正确做法**：测试整条链路必须 PR 合并后再看 Actions，不能指望 PR 里的 CI 验证部署。
> - **现象**：bgg-dev 在国内，`docker compose pull` 六个 ghcr.io 镜像可能要十几二十分钟，`appleboy/ssh-action` 默认 `command_timeout: 10m` 会超时失败。**根因**：`/etc/docker/daemon.json` 的 registry-mirrors（DaoCloud 等）只加速 Docker Hub，**不代理 ghcr.io**；六个 Go 服务镜像体积不小，串行 pull 更慢。**正确做法**：CI `deploy-dev` job 设 `command_timeout: 45m`；`deploy-dev.sh` 用 `docker compose pull --parallel` + 最多 3 次重试（间隔 30s）。若仍经常超时，长期方案是 CI 构建后同步到国内 ACR（阿里云/腾讯云），compose 改拉国内仓库地址。
