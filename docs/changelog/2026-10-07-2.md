# 2026-10-07-2 修 bgg-dev 后台登录：飞书登录缺 App ID + 账号密码登录字典批量查询超时

## 交接摘要（必读，写给下一个没有上下文的新会话）

**在做什么 / 目标**：

> fitness 第一期部署到 bgg-dev 后，后台登录有两个问题：
> 1. 点「飞书登录」提示「未配置飞书 App ID（VITE_FEISHU_APP_ID）」。后台扫码登录组件 `FeishuQrLogin.vue` 在构建期读 `import.meta.env.VITE_FEISHU_APP_ID`，本机靠 gitignore 的 `admin-frontend/.env.local` 提供，CI `deploy-frontend` 构建时从没传过，所以线上后台飞书登录一直不可用（手机端 fitness 从后端 `/fitness/login/config` 拿 appId，不受影响）。
> 2. 账号密码登录失败，控制台 `POST /gateway/api/v1/dict/batch 400`，`context deadline exceeded`。iam-rpc 的 `DictBatchGet` 对每个编码串行查库（`FindByCode` + 缓存未命中时 `FindByTypeID`），后台登录一次拉约 40 个编码，bgg-dev 用的外部 MySQL 单次往返几十到上百毫秒，累计超过网关调 iam 的 2s RPC 超时；fitness 往 `REQUIRED_DICT_CODES` 加了 7 个编码，把原本贴着超时线的耗时推过了线。前端 `afterLoginSuccess` 又是 `await loadDicts()`，字典失败直接让整个登录失败。

**已完成**：

> - CI：`.github/workflows/ci.yml` 的 `deploy-frontend` →「构建前端」步骤加 `env: VITE_FEISHU_APP_ID: ${{ secrets.FEISHU_APP_ID }}`，Secret 为空时打 `::warning::` 但不中断构建。用户选了「CI 注入仓库 Secret」，没选「后台登录也改成后端下发 appId」（要动 `.api`/RPC）和「后台直接调 `/fitness/login/config`」（后台登录依赖 fitness 域接口）。代价是 appId 在 bgg-dev `admin-server/.env` 和 GitHub 仓库 Secret 各存一份，换飞书应用时两处都要改
> - iam-rpc：`DictBatchGet` 改成固定最多两次查库——`DictTypeRepository.FindByCodes`（`code IN (...)`）一次查出全部字典类型，逐个查 Redis 字典项缓存，未命中的合并成 `DictItemRepository.FindByTypeIDs`（`type_id IN (...)`）一次查出；不存在的编码照旧缺省不报错，查库失败改为直接返回错误（原来逐个 `continue` 吞错）。单测 `dictbatchgetlogic_test.go` 用 sqlmock 断言 3 个编码（含重复、空串、不存在）只发 2 条 SQL、缓存命中时不查字典项
> - 前端：`stores/user.ts` 的 `afterLoginSuccess` 里字典加载失败不再拦登录（`DefaultLayout.vue` 进后台时发现 `dictStore.loaded=false` 会重拉），`user.spec.ts` 补「字典失败登录仍成功」用例
> - 核对过 bgg-dev 后端：`FEISHU_APP_ID` 已配置、`FEISHU_REDIRECT_URI` 与前端拼出的回调地址 `https://oldbai.top/bgg/admin/login/feishu/callback` 一致

**踩过的坑 —— 绝对不要再犯**：

> - 现象：本机后台飞书登录正常，部署到 bgg-dev 后提示未配置 App ID。根因：`VITE_*` 变量是 Vite 构建期内联的，本机来自 gitignore 的 `.env.local`，CI runner 上不存在这个文件，构建产物里 appId 就是空字符串。正确做法：新增任何 `VITE_*` 变量时，同步在 `ci.yml` 的 `deploy-frontend` 构建步骤用 `secrets.*` 注入，并在仓库 Secrets 里配好（值不写进仓库/文档）；或者像 fitness 那样改成运行时从后端接口下发。
> - 现象：本机联调登录正常，bgg-dev 上 `/dict/batch` 稳定 2s 超时、登录失败。根因：批量接口里按编码循环查库，本机库延迟低看不出来，外部托管库每次往返几十到上百毫秒，N 个编码就是 N~2N 次往返；超时中断后后半截编码的缓存也写不进去，下次登录照样冷启动。正确做法：批量接口一律用 `IN (...)` 合并查询，查库次数不随入参个数增长；往 `REQUIRED_DICT_CODES` 这类「登录时一次拉全」的列表里加编码时，要意识到它会放大这类问题。
> - 现象：交接记录/PR 描述里写了飞书 appId、tenant_key 的真实值。根因：把「不是密钥」当成「可以公开」。正确做法：仓库、changelog、PR 描述里的配置项只写变量名和「与 bgg-dev `.env` 相同」，真实值只留在服务器 `.env` 和 GitHub Secrets。
